# PageIndex를 활용한 RAG 검색 구현 계획

`pageindex` 브랜치에 EnterpriseRAG-Bench용 검색 방식 `pageindex`를 추가한다. 질문이 들어오면 열람 가능한 문서에서 후보를 고르고, 후보 문서의 목차를 따라 답을 담고 있는 문장을 찾아 기존 답변기에 넘긴다. 첫 실험에서는 **정답 문서를 찾았는지**와 **그 문서 안에서 답을 뒷받침하는 구간까지 찾았는지**를 각각 측정한다.

## 오픈소스 적용 범위

PageIndex의 MIT 공개 소스 `0.2.10`, 커밋 `add6b17cebff528612748ede3fed565b5f726c6b`를 기준으로 한다. 이 버전의 로컬 `PageIndexClient.submit_document()`는 PDF를 받는다. 같은 저장소의 `pageindex.page_index_md.md_to_tree()`는 Markdown 파일에서 제목, 문서 내 노드 ID, 1부터 시작하는 행 번호, 자식 노드를 반환한다. 우리 데이터는 본문이 이미 텍스트이므로 Markdown 경로를 직접 호출하면 OCR과 PDF 변환이 필요 없다. [PageIndex Markdown 구현](https://github.com/VectifyAI/PageIndex/blob/add6b17cebff528612748ede3fed565b5f726c6b/pageindex/page_index_md.py) · [로컬 PDF 입력 구현](https://github.com/VectifyAI/PageIndex/blob/add6b17cebff528612748ede3fed565b5f726c6b/pageindex/local_api.py) · [버전과 라이선스](https://github.com/VectifyAI/PageIndex/blob/add6b17cebff528612748ede3fed565b5f726c6b/pyproject.toml)

**PageIndex가 맡는 부분은 문서별 목차 생성이다.** 프로젝트에서 구현할 부분은 소스별 본문의 구조화, 여러 문서 중 후보 선택, LLM의 목차 탐색, 원문 위치 복원이다. 실험 결과에는 이 조합을 `PI`로 표시한다. 비교군은 C0 키워드, C1 벡터, C2 하이브리드다. 기존 로드맵의 C3는 하이브리드 기반 다단계 검색을 가리킨다. [기존 실험 조건](../README.md#experiment-conditions)

## 문서를 색인하는 방법

1. **원문과 목차를 연결한다.** PostgreSQL의 `documents.content`를 인용 기준으로 삼는다. 원본 JSON을 사용할 수 있으면 현재 정규화기가 `content_field_names` 순서로 본문을 조립할 때 각 필드의 시작·끝도 계산한다. 조립 결과가 저장된 본문과 같은지 확인한다. 이렇게 하면 기존 DB도 같은 입력을 읽어 트리를 추가할 수 있다. TXT·Parquet나 원본 JSON이 없는 DB는 저장된 본문의 제목·문단·발언 경계를 사용하고, 어느 규칙을 사용했는지 기록한다. [정규화 코드](../src/enterprise_agent/ingestion/normalize.py) · [입력 로더](../src/enterprise_agent/ingestion/loader.py)
2. **실제 문서 구조를 Markdown 제목으로 표현한다.** Fireflies는 회의 제목 아래에 요약·후속 조치·전사를 두고, 긴 전사는 연속된 발언을 묶어 실제 시각을 표시한다. Confluence는 본문의 기존 제목을 활용한다. 짧은 Slack 메시지는 본문 하나로 충분하다. 제목이 없는 긴 글은 문단을 토큰 예산 안에서 묶고, 단일 문단이 예산을 넘으면 문장 또는 원문 위치에서 나눈다. 제목과 검색용 발췌는 길을 찾는 데만 쓴다. 인용 가능한 텍스트는 원문에서 복원한다.
3. **위치를 색인과 함께 만든다.** Markdown을 쓸 때 각 본문 행·구간이 원문의 어느 유니코드 문자 구간 `[start, end)`에 해당하는지 기록한다. 새로 붙인 제목에는 인용 구간을 부여하지 않는다. `md_to_tree()`의 `line_num`과 이 표를 연결해 노드 자신의 본문과 자식 범위를 구분한다. 같은 문장이 여러 번 나와도 해당 위치를 보존한다. 첫 버전은 노드 ID를 켜고, 노드 병합과 LLM 요약은 끈다. 탐색 모델에는 원문의 제목·발췌로 만든 짧은 설명을 제공한다.
4. **변경된 문서만 다시 색인한다.** 제안 테이블 `pageindex_documents`에 원본 `dsid_*` 외래 키, 문서 지문, 색인 설정 버전, 트리와 위치표를 저장한다. 노드 ID는 해당 문서와 색인 버전 안에서만 유효하다. 문서 한 건의 트리를 완성한 뒤 트랜잭션에서 최신 지문을 대조하고 교체한다. 삭제는 부모 문서에 연동하고, 빈 본문은 처리 완료로 기록한다. 실패 후 재개할 때 완성된 동일 버전은 재사용하며, 검색은 현재 지문과 일치하는 트리만 읽는다.

## 질문에서 원문 근거까지

| 단계 | 입력과 처리 | 확인할 결과 |
| --- | --- | --- |
| 1. 권한 적용 | 제목·발췌를 읽기 전에 DB에서 허용 소스·문서 ID, 요청의 소스·메타데이터 필터를 교차 적용한다. 트리와 본문을 읽을 때도 적용한다. | 빈 허용 목록이면 모델 호출 0회. 권한이 없는 제목·요약도 모델에 전달되지 않는다. |
| 2. 문서 선택 | 첫 실험에서는 허용된 문서 전체의 제목·소스·짧은 발췌를 토큰 예산에 맞춰 묶는다. LLM이 각 묶음에서 복수 후보를 선택하고, 후보를 모아 질문과 관련된 순서로 최대 20개 문서를 고른다. | 질문만으로 후보를 정한다. 어느 단계에서 정답 문서를 놓쳤는지 사후 분석할 수 있도록 후보 순위를 보관한다. |
| 3. 트리 탐색 | 후보 문서의 제목·발췌와 자식 목록을 깊이별로 묶어 보여 주고, LLM이 읽을 노드를 선택한다. 선택한 구간의 원문을 읽고, 서버가 붙인 문장·발언 ID 중 근거가 되는 것을 질문 관련도순으로 반환하게 한다. | 서버는 요청에 제시한 문서·노드·구간 ID만 수락한다. 여러 문서의 보완·상충 근거도 반환할 수 있다. |
| 4. 검색 결과 구성 | 선택한 구간 전체를 담은 기존 청크를 우선 사용한다. 경계를 넘으면 실제 청크 여러 개로 나눠 덮고 중첩 구간을 중복 인용하지 않는다. 근거가 있는 문서만 남겨 후보 순위대로 문서당 첫 청크를 내고, 다음으로 각 문서의 추가 근거를 낸다. 동률은 문서 ID와 원문 위치로 푼다. | 기존 `SearchHit`에 실제 `chunk_id`와 선택한 근거 범위를 담는다. `score`가 필요한 곳에는 최종 순위의 역수를 쓰고 모델의 확률과 구별한다. |
| 5. 답변과 인용 | 기존 답변기가 DB에서 근거를 재조회한다. `select_passages()`가 선택된 범위를 우선 배정해 긴 청크의 뒤쪽에 있는 근거도 생성기에 전달한다. 생성 후 권한·원문 일치·주장 지지 검사를 거친다. | 인용의 `quote`가 `documents.content[start:end]`와 일치한다. 근거가 부족하면 부분 답변 또는 보류로 처리한다. |

현재 답변기는 DB의 청크를 다시 읽고, 각 청크 **앞부분**부터 문맥 예산을 배정한다. 트리가 찾은 문장을 생성기가 실제로 보도록 선택 범위를 답변기까지 전달한다. PageIndex 검색 CLI와 답변 API에는 운영자가 설정한 `ANSWER_ACCESS_SCOPE`를 적용하고, 비교 평가에는 동결된 표본 전체에 대한 읽기 범위를 명시한다. [검색·권한 필터](../src/enterprise_agent/storage/search.py) · [근거 선택과 인용](../src/enterprise_agent/validation/citations.py) · [답변 파이프라인](../src/enterprise_agent/generation/service.py)

탐색은 로컬 모델의 구조화된 응답으로 시작한다. 개발용 초기 한도는 질문당 후보 문서 20개, 모델 호출 32회, 그 안에서 형식 오류 재시도 1회다. 한 요청의 입력 예산은 모델 문맥 길이에서 출력 토큰을 예약해 정하고, 전체 질의에는 시간 제한을 둔다. 한도에 닿으면 확보한 근거와 종료 사유를 기록한다. 모델 연결 장애는 실행 오류로 집계한다. 검색 모델·프롬프트·한도는 별도 개발 질문에서 확정하고, 최종 평가 동안 고정한다.

## GCP 회의록으로 확인할 예시

공식 질문 `qst_0004`는 “새 구독의 권한 반영이 늦을 때 GCP 팀은 온보딩 화면에서 어떻게 처리하라고 권했는가?”를 묻는다. 기존 C2는 해당 Fireflies 회의록을 이미 **문서 1위**로 찾았다. 이 사례에서 확인할 개선점은 사용자가 물은 처리 방법이 있는 발언까지 도달하는지다. [기존 문서 순위 검산](phase1-2-verification.md)

기대하는 검색 경로는 **회의록 → 전사 → 03:14를 포함한 발언 묶음 → Anika Desai의 발언**이다. 현재 정규화된 원문에서 발언 전체는 `[6108, 6422)`이고, 구독이 동기화 중이니 몇 분 뒤 다시 시도하라는 문구는 `[6332, 6393)`에 있다. 발언 전체는 기존 청크 경계를 넘지만 해당 문구는 한 청크에 담긴다. 회의록 순위, 선택한 구간, 최종 인용의 원문 일치를 각각 검사한다. 이 문서 ID와 시각은 사후 대조에만 사용한다.

## 구현 순서와 완료 기준

| 순서 | 변경할 곳 | 단계 완료 기준 |
| --- | --- | --- |
| 1. 오픈소스 연결 | `pyproject.toml`의 선택 의존성, `uv.lock`, Markdown 입력 어댑터 | Python 3.11에서 고정 리비전 설치. 실제 `md_to_tree()`로 긴 회의록과 짧은 메시지의 계층·행 번호를 확인한다. |
| 2. 색인과 저장 | `ingestion/`, `storage/schema.sql`, `build-index --kind pageindex` | 9개 소스 180문서의 색인 상태를 확인한다. 비어 있지 않은 문서의 본문 구간을 원문과 대조하고 재실행·수정·삭제·동시 빌드·중단 후 재개를 검증한다. |
| 3. 검색기 | `retrieval/`, `storage/search.py`, CLI `search --method pageindex` | 공통 `search(query, k, filters)`로 실제 문서·청크를 반환한다. 로컬 모델 연결, 빈 권한, 잘못된 노드 ID, 시간 초과, 복수 문서 선택을 테스트한다. |
| 4. 답변 연결 | `models.py`, `generation/contracts.py`, `validation/citations.py`, CLI `answer`, FastAPI `POST /answer` | 두 진입점에서 같은 방식으로 검색한다. 권한 변경, 청크 경계, 근거가 뒤쪽에 있는 경우, 무근거 보류를 검증한다. 인용 원문 불일치와 권한 밖 근거 노출은 각각 0건이어야 한다. |
| 5. 비교 평가 | `cli.py`, `storage/snapshot.py`, `evaluation/`, `experiments/` | `evaluate --methods`로 실험 대상을 선택한다. 현재 평가기는 항상 임베딩을 초기화하고 전체 커버리지를 요구하므로, 공통 코퍼스 지문과 방식별 색인 커버리지 검사를 분리한다. PI 단독 평가는 벡터 0건인 DB에서도 실행하고, C1·C2를 포함하면 기존 벡터 검사를 수행한다. |

구현 후에는 아래 명령으로 180문서가 수집된 DB에서 색인·검색·비교 평가를 실행한다. 검색 예시는 Fireflies 열람 권한과 로컬 탐색 모델이 설정된 환경을 전제한다.

```bash
uv run enterprise-agent build-index --kind pageindex --input EnterpriseRAG-Bench
uv run enterprise-agent search 'How should onboarding handle a delayed subscription entitlement?' --method pageindex --top-k 5
uv run enterprise-agent evaluate --methods keyword dense hybrid pageindex \
  --questions EnterpriseRAG-Bench/questions.jsonl --limit 500 --chunk-depth 50 \
  --dataset-version d36685e273713975ee20299bbf1ab64165575b3c \
  --output experiments/results/pageindex-sample180.json
```

## 성능을 판단할 기준

- **기존 세 방식과 같은 조건에서 비교한다.** 같은 180문서, 공식 500문항, 같은 원문 청크(1,200자·겹침 160자), 결과 깊이 최대 50청크를 사용한다. 트리의 분할 단위는 소스 구조를 따른다. 기존 세 방식의 순위를 저장된 결과와 대조한 뒤, 네 방식 모두 반환된 근거의 `dsid_*`를 최초 등장 순서로 중복 제거해 Recall@1·5·10과 MRR을 계산한다. 실제 반환한 고유 문서 수도 기록한다. 현재 C2의 비교값은 Recall@1 **3.40%**, Recall@10 **4.18%**다. [기존 평가 설정과 수치](phase2-sample180-summary.json) · [지표 정의](../src/enterprise_agent/evaluation/metrics.py)
- **문서 누락과 탐색 실패를 구분한다.** 공식 500문항 중 정답 문서 ID가 있는 470개가 문서 지표의 분모다. 이 중 표본에 정답이 하나라도 있는 24문항은 별도로 집계한다. 두 집계 모두 질문별 전체 정답 수를 Recall의 분모로 유지하고, 최소 한 개를 찾은 질문 수도 표시한다. 이 표본의 전체 Recall@10 상한은 약 4.60%다. 문서 후보 단계의 Recall과 최종 근거를 반환한 문서의 Recall을 함께 기록한다. [표본 커버리지 검산](phase1-2-verification.md)
- **답을 담은 구간을 찾았는지 채점한다.** 원문 일치 여부와 질문에 필요한 정보가 그 구간에 있는지를 따로 본다. 개발 사례의 근거 구간을 사전에 표시하고, 동일한 반환 깊이 또는 문맥 예산에서 C2와 PI가 그 근거를 얼마나 포함하는지 대조한다. 답변 비교에는 같은 생성 모델·프롬프트·문맥 예산을 사용한다. 공식 정답·사실·기대 문서 ID는 평가기에만 둔다.
- **시간과 비용을 측정한다.** 색인 시간·저장량, 질의 지연 p50/p95, 선택한 문서·노드 수, 호출·재시도·토큰, 예산 소진 및 오류 건수를 기록한다. 비교 보고서에는 코퍼스·질문 해시, PageIndex 커밋, 모델·프롬프트·색인 버전, 캐시 상태를 남긴다. 실패한 질문도 집계에 포함하고, 모델을 다시 실행했을 때의 순위 변동을 확인한다.
- **문서 수를 늘릴 때의 효과를 검증한다.** 180문서는 동작과 실패 원인을 확인하는 표본이다. 다음에는 정답과 독립적으로 소스별 고정 표본을 확대해 문서 수에 따른 Recall과 질의 비용을 측정한다. 전체 약 51만 문서에서는 허용 문서 전체의 설명을 매번 읽는 비용이 커지므로, 같은 C2 문서 후보에 기존 근거 선택과 PageIndex 트리 탐색을 각각 적용하는 대조 실험을 설계한다. 이 결과에는 C2가 후보를 공급했다는 조건을 표시하고, 비용 차이와 후보 누락을 함께 보고한다.

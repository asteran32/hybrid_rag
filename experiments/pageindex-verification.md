# PageIndex 검색 구현 검증

2026년 11월 22일, `pageindex` 브랜치의 `e907ed4`에서 EnterpriseRAG-Bench의 9개 소스별로 20문서씩 색인했다. 검증 범위는 이 180문서에서의 검색과 근거 인용이다.

## 공식 500문항의 검색 결과

**정답이 표본에 들어 있는 24문항에서 하이브리드는 22문항, PageIndex는 2문항의 정답 문서를 상위 10위 안에 반환했다.** PageIndex는 24문항 중 3문항에서만 정답 문서를 후보로 골랐다. 이 실행에서 가장 많은 정답을 놓친 지점은 문서 선택 단계였다. [평가 요약과 문항 수 검산](pageindex-sample180-summary.json)

| 검색 방식 | 문서 Recall@1 | Recall@5 | Recall@10 | MRR | 상위 10위에 정답이 있는 문항 | 지연 p50 | 지연 p95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| C0 키워드 | 2.98% | 3.40% | 3.86% | 0.03455 | 20/24 | 18.22ms | 37.15ms |
| C1 벡터 | 2.23% | 3.51% | 4.18% | 0.03020 | 22/24 | 6.34ms | 8.98ms |
| C2 하이브리드 | 3.40% | 4.07% | 4.18% | 0.03938 | 22/24 | 19.41ms | 41.85ms |
| PI PageIndex | 0.43% | 0.43% | 0.43% | 0.00426 | 2/24 | 21.82초 | 57.45초 |

Recall과 MRR은 정답 문서 ID가 있는 470문항의 평균이다. 질문마다 상위 k개 고유 문서에서 찾은 정답 문서 수를 그 질문의 정답 문서 수로 나눈다. 446문항은 180문서 표본에 정답이 하나도 없어 이 표본의 전체 Recall@10 상한은 4.60%다. 표본에 정답이 있는 24문항만 놓고 계산한 평균 문서 Recall@10은 C2가 81.77%, PI가 8.33%다. 위 표의 22/24와 2/24는 상위 10위에서 정답을 **하나 이상** 찾은 질문 수다. 지연에는 500문항 모두를 포함하며 답변 생성 시간은 별도다.

PageIndex가 반환한 후보는 질문당 평균 2.74문서였고, 탐색한 노드는 평균 9.62개였다. 최종 근거가 있는 고유 문서는 평균 0.80개, 검색 결과가 비어 있는 질문은 129개였다. 정답 후보가 있었던 세 질문 가운데 `qst_0051`과 `qst_0064`는 최종 문서 1위에서 정답을 찾았다. `qst_0108`은 후보 2위에 정답이 있었지만 최종 근거는 다른 문서에서 반환했다.

500문항에 로컬 모델을 6,119회 호출했다. 문서 선택에 5,002회, 목차 선택에 589회, 근거 선택에 528회가 들었다. 이 합계에는 형식 오류 재시도 36회가 포함된다. 응답에서 집계한 입력은 5,833,388토큰, 출력은 370,687토큰이다. 종료 사유는 정상 완료 494문항, 잘못된 선택 2문항, 모델 응답 시간 초과 4문항이었다. 시간 초과 4문항 모두 표본에 정답이 없었다. 평가기는 500문항 전체를 결과 파일에 기록한 뒤 이 오류를 알리는 종료 코드 1을 반환했다. PI 질의 지연의 합은 약 3시간 44분이었고 외부 모델 API 요금은 0원이었다.

시간 초과 4문항을 같은 설정으로 다시 실행했다. `qst_0307`과 `qst_0364`는 각각 68.79초와 75.50초에 완료했고, `qst_0356`과 `qst_0490`은 두 번째에도 120초 한도에 도달했다. 표의 공식 집계에는 500문항의 최초 실행을 사용했다. [시간 초과 문항의 재실행 기록](results/pageindex-timeout-replay.json)

### GCP 회의록에서의 문서 순위와 근거 순위

공식 질문 `qst_0004`는 새 구독의 권한 반영이 늦을 때 온보딩 화면에서 어떻게 안내할지를 묻는다. C2는 해당 Fireflies 회의록을 **문서 1위**로 찾았고, “동기화 중이니 몇 분 뒤 다시 시도하라”는 원문 구간 `[6332, 6393)`을 포함한 청크는 **11위**에 반환했다. 같은 질문에서 PI는 해당 회의록을 후보에 올리지 못했고 최종 검색 결과도 비어 있었다. 문서 순위와 근거 구간 순위를 각각 평가하는 이유를 보여 주는 사례다. [질문별 원시 결과](results/pageindex-sample180.json)

### 근거 위치와 답변 인용 검산

이전 실행과 질문·코퍼스 지문을 대조했다. C0·C1·C2의 1,500개 질문별 결과에서 문서 순위·지표와 청크 ID·순위·점수·구성 검색기 순위가 일치했다. PI의 500개 결과에 대해서는 평가기와 별도로 문서 순위를 재구성해 Recall과 MRR을 다시 계산했다. 탐색 기록 4,811개가 모두 해당 후보 문서에 존재하는 노드를 가리켰다. 반환한 원문 구간 1,396개도 DB의 문서·청크 문자 위치와 모두 일치했다. 원문 일치 검사는 아래의 질문별 근거 적중 검사와 구분된다. [측정값과 검산 결과](pageindex-sample180-summary.json)

정답 구간을 미리 표시한 개발 질문 3개를 180문서 전체에서 검색했다. 아래 값은 상위 k개 청크에 표시된 구간 전체가 들어간 질문 수다. C2는 반환한 청크 본문 전체, PI는 해당 청크에서 모델이 근거로 선택한 문자 구간을 사용한다. 개발 질문에는 구현 계획에 든 공식 GCP 사례를 바꿔 쓴 질문이 하나 포함된다. [근거가 표시된 개발 질문](pageindex-development.jsonl)

| 개발 질문 3개 | 상위 1청크 | 상위 5청크 | 상위 10청크 |
| --- | ---: | ---: | ---: |
| C2 하이브리드 | 2/3 | 3/3 | 3/3 |
| PI PageIndex | 0/3 | 0/3 | 0/3 |

PI는 가격 고정을 묻는 개발 질문에서는 정답 문서를 1위로 찾았고, 그 안에서 표시된 근거와 다른 구간을 골랐다. 세 개발 질문을 같은 설정으로 다시 실행했을 때 후보 문서, 탐색 노드, 최종 문서·청크 순위와 선택한 원문 범위가 모두 첫 실행과 일치했다.

**범위를 좁힌 답변 예시.** Linear 소스 안에서 “교대 근무용 보조 패널은 어느 화면에 있는가?”라고 물었다. PI의 CLI와 FastAPI `POST /answer` 모두 **Alerts와 SLO 화면**이라는 부분 답변(`partial`)을 반환했다. 두 경로가 인용한 원문은 같은 문서 `dsid_1d5c022db7ef4708a7178bc291921770`의 `[1010, 1120)`과 일치했다. 같은 질문·범위·생성 모델로 C2도 같은 화면을 답했고, 인용은 `[166, 673)`이었다. FastAPI는 실제 DB·로컬 모델을 연결한 TestClient에서 확인했다. 해당 요청 환경의 허용 범위 밖인 Slack으로 제한한 호출은 인용 없이 보류했다. [CLI·API 원문 대조와 반복 실행 결과](results/pageindex-entrypoints-audit.json)

## 재현과 자동 테스트

전용 DB에 문서와 기본 검색 색인을 준비한 뒤, Qwen 모델을 로컬 Chat Completions 서버에 `local-model`로 띄운다. `PAGEINDEX_BASE_URL`에는 서버의 루프백 주소와 `/v1` 경로를 지정한다. 이 측정에서는 서버 옵션 `-c 8192 -np 1 --cache-ram 640`을 사용했다. `PAGEINDEX_TOKENIZER_PATH`에 위 리비전의 `tokenizer.json`을, `PAGEINDEX_MODEL_REVISION`에 가중치 SHA-256을 지정한다. [DB와 모델 준비 방법](../README.md#getting-started)

```bash
uv sync --locked --python 3.11 --all-extras
uv run --locked enterprise-agent build-index --kind pageindex --input EnterpriseRAG-Bench
uv run --locked enterprise-agent evaluate --methods keyword dense hybrid pageindex \
  --questions EnterpriseRAG-Bench/questions.jsonl --limit 500 --chunk-depth 50 \
  --dataset-version d36685e273713975ee20299bbf1ab64165575b3c \
  --output experiments/results/pageindex-sample180.json
```

집계 수치·사례·지문은 Git에 보관했다. 질문별 원시 결과는 위 명령이 생성하는 로컬 파일이다. 공식 500문항에서는 문서 검색을 채점했고, 생성 답변은 위 Linear 사례에서 인용 원문과 함께 검사했다. [보관된 평가 요약](pageindex-sample180-summary.json)

PostgreSQL에 연결해 `pytest -q`를 실행한 결과 80개 테스트가 통과했다. PageIndex 의존성에서 PyPDF2 사용 중단 경고가 한 번 발생했다. 테스트에는 동시 색인과 중단 후 재시도, 문서 권한과 메타데이터 필터, 잘못된 모델 선택과 호출 한도, 청크를 가로지르는 인용, 벡터 없는 DB에서의 PI 단독 평가가 포함된다. `uv lock --check`, Ruff 검사와 포맷 검사, wheel 빌드도 통과했다. wheel에서 색인·검색 모듈, DB 스키마, 선택 의존성 `pageindex==0.2.10`을 확인했다.
